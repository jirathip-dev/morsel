## What changed

`FoodImageCompressor`'s synchronous body (validate → `UIImage(data:)` decode →
downsample → JPEG quality search → bounds check) keeps its behaviour, and is now
reached through ONE bounded off-main worker, `MealPhotoPreparationWorker`
(an `actor`: one preparation at a time), from BOTH shipped surfaces:

- Add Meal — `AddMealPhotoSection` (`loadPhoto` library pick, `prepareCameraImage`
  camera capture),
- Edit attachment — `MealPhotoEditorSection` (same two entry points, publishing
  `pendingPhoto`).

A per-surface `MealPhotoPreparationGate` stamps every preparation. A newer pick,
Remove, or leaving the page/sheet retires the older stamp (`invalidate()` +
task cancellation), so a late result **or** error publishes nothing; only a
still-current failure writes the error line, and it never clears the previous
photo/draft (`MealPhotoPreparationGate.apply`). The compressor checks
`Task.checkCancellation()` at each downscale bound, so a superseded preparation
stops early instead of finishing work nobody can publish.

## Why this is an off-main *decode*, not just off-main construction

- `trace.ranOffMainThread` is sampled **inside** the synchronous body
  (`FoodImageCompressor.compressTraced`, first line), i.e. after the actor hop —
  it cannot be satisfied by moving a call site. The whole body that follows
  (including `UIImage(data:)` *and* the `draw(in:)` that performs the lazy
  ImageIO decode inside `resized`) runs on the worker's executor.
- The heartbeat is a real MainActor task (`Task { @MainActor … }` + 1 ms
  `Task.sleep`) that records timestamps while the preparation is in flight.
  BEFORE the window contains **0** ticks (the synchronous call monopolises the
  main actor; deterministic, the main thread never yields), AFTER it contains
  26–35 (measured; the MainActor keeps being serviced → Cancel / navigation
  stay responsive).
- Bite proof that the witness is not decorative: reverting the worker body to the
  caller's actor flips `after_off_main` to `false`, drives the AFTER heartbeat to
  0/2, and fails three assertions (mutation-1 below).

## Bounded concurrency + memory

- `MealPhotoPreparationWorker.peakConcurrentPreparations` is a runtime witness
  recorded by the worker: 4 concurrent `prepare` calls (1600×1200 … 2400×1800
  fixtures) complete with **peak = 1** — one decode/downsample/encode lives in
  memory at a time (mutation-1 shows the witness *can* move: peak 4).
- Output stays within today's constraints: ≤ 2048 px longest edge and
  ≤ 5 MiB (`FoodImageStore.targetMaxBytes`); the 10 MiB source refusal still lives
  at `FoodImageStore.validate(data:mimeType:)` and is asserted in the same suite.
- Oriented fixture: EXIF orientation 6 (raw 3024×4032 portrait, visual
  4032×3024 landscape) keeps its visual aspect after the downsample
  (2048×1536) — an orientation-ignoring path would come out portrait.
- Invalid bytes → `FoodImageError.invalidImage`; non-image MIME →
  `.unsupportedMimeType`; camera path compresses a `UIImage` through the same
  worker.

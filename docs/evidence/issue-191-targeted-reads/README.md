# Issue #191 — replace full outbox/photo scans with targeted reads

Simulator/model witnesses on a throwaway account file: every meal, item and photo payload below is
synthetic (generated bytes, no real health/meal content, no token or signed URL anywhere), and every
byte claim is MEASURED on that real SQLite file. Physical-iPhone feel/HealthKit acceptance stays with
tracker #172; nothing here is a physical-device or live-server run.

Lane base: `89a1f0004b79d7cb5c797c50f508c951dd4ff603` (`origin/staging` when the lane started).
Repro commit (byte instrumentation + the witnesses, RED): `c2e3deb85607be1c1e034d1f4c285b68ef7e5a1e`.
Fix head: `0b6525869bb74e731621a632007dcd849ce0b7ac`.

## What the fix changes

The read/status paths answered questions about ONE row by materializing every queued row's photo
BLOB. Now:

- `LocalDataStore.queuedMealSummaries()` / `queuedMealSummary(mealID:)` project every outbox column
  EXCEPT `photo_data`; the payload's existence and mime type come from the record header
  (`typeof(photo_data) = 'blob' AND photo_mime IS NOT NULL AS has_photo`), never from the bytes.
- ONE parser (`summaryRow`) serves both projections, so a full row and a metadata row can never
  disagree about any field; the full row read adds only the payload itself.
- `queuedPhoto(path:)` derives the meal id that the canonical object path NAMES and keyed-reads
  exactly that row (`queuedMeal(mealID:)`); the canonical-form equality is the same match the old
  scan performed, so which paths resolve is unchanged.
- `merged`, `localMealRecord`, `deleteMealLog`, `queuedMeal(containingItem:)`, `recordMealAttempt`,
  the sync engine's queue enumeration and refusal checks, and the diary index read metadata instead
  of payloads.
- The sync engine still reads each DELIVERED row's durable payload by key, so an upload sends the
  complete photo bytes; the payload always stays durable in the outbox row (no volatile cache).

| item existence check (`confirmMealItem`) | 2,100,000 | 0 |
| item edit's local draft read | 2,100,000 | 0 |

| no-photo queued row's read (falls to the remote) | 2,100,000 | 0 |

| non-canonical path text | 2,100,000 | 0 |

`LocalDataStore.blobBytes(column: "photo_data")` is the counter: it is incremented at the SQLite read
seam (`sqlite3_column_blob`/`sqlite3_column_bytes` materialization), so these are real decoded bytes,
not estimates. The control test proves the counter bites: a full `queuedMeals()` read still costs all
2,100,000 B.

## AC coverage

- **AC1** — one queued thumbnail read fetches only its intended BLOB (`testOneQueuedThumbnailRead…`);
  metadata/status/existence reads fetch zero photo bytes (`testMetadataStatusAndExistence…`,
  `testRevisionLookup…`, the merge/refusal/upload witnesses).
- **AC2** — no-photo and unknown paths fall through safely to the remote, a foreign account's path
  still raises `FoodImageError.invalidPath`, and the canonical/legacy/non-canonical matching is
  unchanged (`testNoPhotoAndUnknownPaths…`, `testForeignAndNonCanonicalPaths…`; the #135/#188 path
  contract tests stay untouched).
- **AC3** — instrumented SQLite-backed tests with several large photo rows; byte counts depend on the
  SELECTED photo, never on the total queued bytes (table above).
- **AC4** — retry/status updates and cached merges retain every field and truthful states
  (`testRetryAndStatusUpdates…`, `testJournalMerge…`); the upload still carries the complete durable
  payload (`testUploadCarriesTheCompleteDurablePayload…`, byte-equal to the row's payload).
- **AC5** — connection/lock ownership is documented on `LocalDataStore` (one connection per account
  file, one `NSRecursiveLock` per store instance held for a single statement, sibling stores own
  their own connections, WAL + 2 s busy timeout between instances). No background path performs a
  queue-wide BLOB scan any more, so the synchronous UI-facing lookup
  (`queuedPhoto` → `loadMealImage` / `mealPhotoRevision`) can only ever queue behind ONE keyed
  statement. `testUIFacingLookupStaysKeyedWhileABackgroundPassIsInFlight` holds a sync pass in flight
  (parked mid-commit on a latch) while the main-actor revision lookup and fetch run against a queue
  of three large photos: each costs exactly the selected photo's bytes (trace line above), and the
  drained pass adds zero further bytes.

## Fence note (disclosed)

`JournalCalendarRepository.swift` (diary index) read the queued DAYS through `queuedMeals()` — the
same audited mechanism (a metadata read materializing every photo BLOB). Its two call sites now use
`queuedMealSummaries()`; the mapping to day buckets is byte-for-byte the same expression. This file is
adjacent to the brief's named read-path files; it is disclosed here rather than left as an
AC1-violating read path. No other file outside the fence was touched.
